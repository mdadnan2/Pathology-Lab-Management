# Feature Spec: Results and Reports

See [results-reports.instructions.md](../../.github/instructions/results-reports.instructions.md) for implementation rules.

## Result entry workflow

1. Technician opens **Results** in the dashboard for collected or processing orders.
2. For each test, enters parameter values and optionally adds notes.
3. The API compares numeric values with configured ranges and sets `isAbnormal`; client flags are never trusted.
4. Technician saves as `DRAFT` or submits a complete result for review.
5. Pathologist moves a submitted result to `UNDER_REVIEW`, then approves it or rejects it with a reason.
6. After rejection, a Technician can edit and resubmit the result.

The `POST /api/v1/results/items/:orderItemId` route saves a draft,
`POST /api/v1/results/:id/submit` submits it, and
`PATCH /api/v1/results/:id/review` moves it through review. Result reads are
restricted to OWNER, ADMIN, TECHNICIAN, and PATHOLOGIST; Technicians can see
eligible unentered items and only their own saved results.

## Result status machine

```
DRAFT → SUBMITTED → UNDER_REVIEW → APPROVED
                  ↘ REJECTED → DRAFT (re-entry allowed)
```

## Report generation

Prerequisites:
- All `LabOrderItem` results must be `APPROVED`
- Report can only be generated by PATHOLOGIST, ADMIN, or OWNER

The **Reports** screen filters existing reports by status, creation date, or
patient name/code and offers generation only for approved orders that do not
already have a report. Generated reports begin in
`PENDING_APPROVAL`; a Pathologist, Admin, or Owner approves them before they
can be downloaded. Receptionists can view and download approved reports for
delivery. Technician report access is not permitted.

API routes include `GET /api/v1/reports`, `GET
/api/v1/reports/eligible-orders`, `POST
/api/v1/reports/orders/:orderId/generate`, `PATCH
/api/v1/reports/:id/approve`, and `POST /api/v1/reports/:id/download`.
The download route returns a server-generated PDF and records the first
delivery in the report status and audit log. PDF content is generated from
code-controlled text and never renders submitted HTML.

Report PDF contains:
- Header: "DEMO PATHOLOGY LABORATORY — FICTIONAL DEMO DATA"
- Patient: name, code, DOB, gender
- Order: order number, collection date, report date
- For each test: test name, parameters, values, units, reference ranges, abnormal flags
- Approved by: pathologist name, designation
- Footer: "THIS REPORT IS DEMO DATA AND NOT FOR CLINICAL USE"

## Report status machine

```
DRAFT → PENDING_APPROVAL → APPROVED → DELIVERED
```

## UI screens

1. **Results** (`/results`) — per-order-item parameter entry, reference range hints, draft saving, submission, and Pathologist review.
2. **Reports** (`/reports`) — eligible order selection, report approval, result summary, and authorized PDF download.
3. **Report PDF** — generated server-side with patient/order details, parameter values, illustrative ranges, approval details, and demo disclaimers.

## Abnormal value display

- Abnormal values highlighted in red (high) or blue (low)
- `↑` / `↓` indicators next to abnormal values
- Reference range shown alongside each parameter
- Clear disclaimer: "Reference ranges are for demo purposes only"

## Seeded workflow examples

The idempotent demo seed configures illustrative parameters for the demo tests,
adds a fictional lipid result in `SUBMITTED` status for Pathologist review, and
adds an approved CBC/ESR order with a report in `PENDING_APPROVAL`. A seeded
parameter outside its illustrative range demonstrates the abnormal indicator.
All these values are fictional and not medically validated.
